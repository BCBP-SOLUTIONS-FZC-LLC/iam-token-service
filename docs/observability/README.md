# Enterprise Platform Observability Standard — iam-token-service

How this service implements the standard defined and enforced by [platform-gincommon](https://github.com/BCBP-SOLUTIONS-FZC-LLC/platform-gincommon/tree/main/docs/observability) (its `docs/observability/`, shipped with each release). This page covers what is specific to iam-token-service; the standard itself, its rules and the governance process are documented there.

## Platform libraries

| Library | Version | Emits here | Wiring |
|---|---|---|---|
| platform-gincommon | v1.6.0 | `platform_http_*`, `platform_build_info`, `platform_library_info{library="platform-gincommon"}`; owns the registry and `metricslint` | `gincommon.ObservabilityMiddlewares(cfg)` in `internal/adapter/inbound/http/router.go` (server) and on the consumer's health router; `/metrics` served by `gincommon.MetricsHandler()` on `METRICS_PORT` in all four binaries |
| platform-events/v2 | v2.0.0 | `platform_messages_*`, `platform_retry_total`, `platform_dlq_messages_total`, `platform_outbox_*`, `platform_dependency_request_seconds` (SNS/SQS/codec), `platform_event_propagation_seconds`, ... | `events.InitMetrics(events.MetricsIdentityFromLabels(gincommon.MetricsConstLabels()), gincommon.MetricsRegisterer())` in `metrics.InitLibraryMetrics` |
| platform-pgcommon/v2 | v2.0.0 | `platform_db_*`, labelled `pool="default"` (RLS-scoped app pool) and `pool="reconciler"` (BYPASSRLS enumeration pool, `SystemPoolConfig`) | `pgmetrics.InitWithIdentity(pgmetrics.IdentityFromLabels(...), gincommon.MetricsRegisterer())` in `metrics.InitLibraryMetrics`, before `pgcommon.NewPool` |

All three register on `gincommon.MetricsRegisterer()`, so one scrape serves every collector. Order in all four binaries:

1. `gincommon.InitTracingWithConfig` — traces get the same identity as metrics (`service.namespace`, `deployment.environment.name`).
2. `gincommon.ObservabilityMiddlewares(cfg)` — fixes the identity.
3. `metrics.InitLibraryMetrics` — `events.InitMetrics`, then `pgmetrics.InitWithIdentity`. Must run before `NewPool` (which registers the pool gauges) and before `Register`.
4. `metrics.Register(appEnv)` — builds this service's collectors and **adopts** platform-events' `platform_dependency_request_seconds` / `platform_duplicate_messages_total` (`registerShared`: an identical descriptor returns platform-events' collector instead of registering a second one, which would disable platform-events' own SNS/SQS/codec series).
5. Pools.

This is the reverse of iam-org-membership, which builds the shared collectors first and lets platform-events adopt them. Both orders end with one series set per name; `test/unit/metricsstandard` pins this one.

Database query spans use `gincommon.NewSpanTracer` as `pgcommon.Config.Tracer`; job and consumer spans use `gincommon.NewTracer`, and log lines get `trace_id` from `gincommon.SpanTraceID`. No production code imports OpenTelemetry or the Prometheus client for setup (`check-gincommon-observability.sh` enforces it).

## Identity

| Label | Value | Source |
|---|---|---|
| `domain` | `iam` | `gincommon.Config.Domain` = `OBSERVABILITY_DOMAIN`, default `metrics.ObservabilityDomain` (Helm `observabilityDomain`) |
| `service` | `iam-token-service` | `APP_NAME`, default `iam-token-service`, in **all four** binaries |
| `environment` | `local`, `dev`, `test`, `staging` or `prod` | `APP_ENV`, default `dev`; passed explicitly to metrics, tracing and logging so they cannot disagree. `production` is rejected at startup (Helm `appEnv: prod`) |
| `version` | build version | `BUILD_VERSION` / `-ldflags main.buildVersion`; only on `platform_build_info` |

The rotator and scheduler CronJobs share the server's identity, because the standard requires `iam_token_service_*` series to carry `service="iam-token-service"`. A run is told apart by the Prometheus `job` label (`iam-token-service-rotator`, `iam-token-service-scheduler`) and by its `rotator.<job>` / `scheduler.<job>` span. CronJobs are not pushed to a Pushgateway: each run serves `/metrics` for `ROTATOR_METRICS_SCRAPE_GRACE` / `SCHEDULER_METRICS_SCRAPE_GRACE` (15s) before exiting (`serveMetricsBriefly`), scraped through the `prometheus.io/scrape` pod annotations in `cronjob-{rotator,scheduler}.yaml`.

## Tiers in this service

| Tier | Namespace | Built by | Count |
|---|---|---|---|
| 1 — platform-shared | `platform_*` | The libraries. This service records into two that platform-events owns: `platform_dependency_request_seconds{dependency="openbao", operation=write\|delete}` and `platform_duplicate_messages_total`, built from the registry entry (`registryEntry`) and adopted via `registerShared` | see [inventory](metric-registry.md) |
| 2 — IAM domain-shared | `iam_*` | `iam_rls_violations_total{violation_type}`, built from the registry entry in `registerMetrics` (shared with iam-org-membership, iam-user-profile and iam-audit-log). `iam_offboarding_cascade_total` is proposed ([Proposal 3](../observability-registry-proposals.md)) and withheld until it is a registry entry; `metricslint` rejects an unregistered `iam_*` name | 1 |
| 3 — service-specific | `iam_token_service_*` (frozen, LLD §25) | `prometheus.NewCounterVec` / `NewGauge` / `NewHistogramVec` in `registerMetrics` with gincommon's const labels (`tier3Labels`) | 19 |

Label **values** stay inside the registry vocabulary:

- `platform_dependency_request_seconds{outcome}` ∈ `success`, `error` (`metrics.OutcomeSuccess` / `OutcomeError`); `dependency="openbao"`, `operation` ∈ `write`, `delete`. OpenBao `read`/`list` are deliberately not instrumented ([Proposal 1](../observability-registry-proposals.md)).
- `platform_duplicate_messages_total{queue}` is the fixed `tenant-lifecycle-tokensvc-q` (`queueNameForConsumer`), `event_type` is the envelope type.
- `iam_rls_violations_total{violation_type}` ∈ `cross_tenant_access`, `missing_or_invalid_guc`, `other`; `metrics.AddRLSViolations` maps anything else to `other`.
- Tier 3 `result` / `op` / `consumer` labels are fixed sets and pre-warmed in `registerMetrics`, so dashboards show 0 rather than no data.

No metric carries a high-cardinality label (`tenant_id`, `principal_id`, `credential_id`, `event_id`, ...); those go on logs and spans only.

### Proposed Tier 1 candidates and their Tier 3 predecessors

`platform_dependency_request_seconds` and `platform_duplicate_messages_total` are `proposed` in the registry. Until they are ratified, the Tier 3 counterparts are the authoritative alerting and SLO source. The OpenBao latency is recorded on both at the same call site; the duplicate count is recorded on the Tier 1 series by platform-events' inbox and on the Tier 3 series by the service:

| Proposed | Authoritative until ratified |
|---|---|
| `platform_dependency_request_seconds{dependency="openbao"}` | `iam_token_service_openbao_call_duration_seconds` |
| `platform_duplicate_messages_total` | `iam_token_service_processed_events_duplicates_total` |

The one exception is `IAMTokenServiceSQSReceiveErrors`, which queries `platform_dependency_request_seconds_count{dependency="sqs"}` because the library's SQS receive errors have no Tier 3 predecessor; it carries `metric_status: proposed`.

### Who counts what (no double counting)

- `platform_dlq_messages_total` is counted **only** by platform-events, once per forward; here that is the outbox dead-letter (`operation="outbox_publish"`). The consumer emits none: it does not use platform-events' `WithMaxReceiveCount`, so a message SQS itself moves to the DLQ after `maxReceiveCount` is counted by nothing in-service — `platform_dlq_depth` is the signal.
- The consumer's own straight-to-DLQ sends (`cmd/consumer/dlq.go`) are `iam_token_service_consumer_dlq_rejects_total{reason}`, one per successful send: `schema_violation` (the payload failed the consumed schema; each violation is also on `iam_token_service_consumed_schema_violations_total{event_type}`, which backs the alert) and `invalid_envelope_id` (a `TenantMembershipsPurged` with no usable dedup id; `IAMTokenServiceOffboardingInvalidEnvelopeRejected`). If the DLQ send fails, neither counter for the send moves and the message falls back to SQS redrive.
- `platform_duplicate_messages_total` is counted by platform-events' inbox (`inbox.Store.Process`, queue from the queue URL); the service counts only the Tier 3 `iam_token_service_processed_events_duplicates_total{consumer}` (`processOnce` in `internal/adapter/inbound/consumer/dedup.go`), as in iam-org-membership.
- `platform_messages_{received,processed,failed}_total` are counted by the SQS consumer; the service never records them.
- `iam_rls_violations_total` is counted by `cmd/server`'s exporter only (see below). Every server replica counts the same rows, so use `max` across pods for magnitudes; the alerts use `max by (...) (increase(...)) > 0`.
- `platform_queue_depth` / `platform_dlq_depth` are sampled by platform-events in `cmd/consumer` every `SQS_QUEUE_DEPTH_INTERVAL` (default 60s, `0s` disables); every replica samples the same queue, so alerts use `max`.
- `platform_http_request_timeouts_total` is counted by gincommon's `TimeoutMiddleware`, which runs inside the observability stack (`gincommon.Config.RequestTimeout`, 30s), so metrics, the access log and the span record the same 503 the client gets.

## RLS violations

`rls_check_tenant()` (migration `000003_rls_violation_log`) still fails closed, and now also samples each failed check into `rls_violation_log`: `missing_or_invalid_guc` when `app.tenant_id` is missing or malformed, `cross_tenant_access` when a row belongs to another tenant. The sample rate is 1% (`app.rls_violation_sample_rate` overrides it; the Postgres tests set 1).

- `cmd/server` runs `runRLSViolationExporter` every `RLS_VIOLATION_EXPORTER_INTERVAL` (1m) over the BYPASSRLS `reconciler` pool. It keeps an id cursor so each row is counted once per pod, and starts one interval back so a restart doesn't re-add the table's history.
- `cmd/rotator` prunes rows older than `RLS_VIOLATION_LOG_TTL_DAYS` (30) through the `SECURITY DEFINER` function `prune_rls_violation_log()`. The app role has no direct grant on the table.
- **Limit:** a cross-tenant *write* rejected by `WITH CHECK` raises an error, which rolls the log row back with the caller's transaction (Postgres has no autonomous transactions). The write is still rejected and the caller gets the error; only reads hidden by RLS and missing-GUC queries reach the log. iam-org-membership has the same limit.
- `test/postgres/rls_violation_log_test.go` checks that every tenant-scoped repository call, run with other tenants' rows present, logs nothing.

## Adding a metric

1. Decide the tier with the standard's decision tree. A new `platform_*` or `iam_*` metric is a registry PR to platform-gincommon, never a local definition; document the proposal in [`../observability-registry-proposals.md`](../observability-registry-proposals.md).
2. Tier 3: add the collector to `registerMetrics` in `metrics.go` as `iam_token_service_<name>` with `ConstLabels: tier3Labels()`: `_total` (counter), `_seconds` (histogram) or no suffix (gauge), snake_case labels, no `*_id`/`email`/`ip` labels. Add it to the `MustRegister` call (an unregistered collector never reaches `/metrics` — see `TestRegister_IsIdempotentAndRegistersAllCollectors`) and pre-warm bounded label values.
3. Record one representative sample in `exerciseEveryCollector` (`test/unit/metricsstandard/standard_test.go`) so `metricslint` validates its labels.
4. Run `make metrics-inventory` and commit the regenerated [`metric-registry.md`](metric-registry.md).
5. If it backs an alert, add the alert to **both** `deploy/monitoring/app-alerts.yml` and `deploy/helm/templates/prometheusrule.yaml`, and its runbook entry to [`runbooks.md`](runbooks.md).

## Items awaiting ratification

- **Tier 1 candidates with a Tier 3 predecessor:** `platform_dependency_request_seconds`, `platform_duplicate_messages_total` (see above).
- **Tier 2 candidate:** `iam_offboarding_cascade_total` ([Proposal 3](../observability-registry-proposals.md)). Not emitted; `iam_token_service_offboarding_cascade_total` is the only cascade metric. On ratification its `outcome` vocabulary becomes the registry's `success | failure | error`.
- **IAM's Tier 2 metric** `iam_rls_violations_total` is `proposed` and needs an IAM owner (registry OQ-4); shared with iam-org-membership, iam-user-profile and iam-audit-log.
- **The libraries' own metrics:** `platform_http_*`, `platform_build_info`, `platform_outbox_*`, `platform_db_*`, ... — owned by the libraries; allowed via `-allow-proposed-owner`.

## SLOs

Recording rules and burn-rate alerts in `deploy/monitoring/slo-rules.yml`. Targets come from the LLD (§11, "SLOs"), except SLO-3's, which is an operational proxy.

| SLO | SLI (recording rule) | Target | Alerts |
|---|---|---|---|
| SLO-1 TS-1 issue/rotate latency | `iam_token_service:ts1_latency_sli:ratio_rate_{5m,1h}`: share of `POST …/service-accounts/:principal_id/credentials` requests at or under `le="0.5"` in `platform_http_request_duration_seconds` | p99 ≤ 500 ms (LLD). The SLI includes the OpenBao write the LLD excludes, so it is conservative | `IAMTokenServiceSLO1_TS1LatencyFastBurn` (14.4×, page), `IAMTokenServiceSLO1_TS1LatencySlowBurn` (6×, ticket) |
| SLO-2 write-path availability | `iam_token_service:write_error_rate:ratio_rate_5m`: `status_class="5xx"` share of `POST\|PUT\|PATCH\|DELETE` in `platform_http_requests_total` (4xx such as `credential_replay_revoked` are intentional) | 99.9% (LLD / HLD §3.4) | `IAMTokenServiceSLO2_WriteErrorRateFastBurn` |
| SLO-3 rotation sweep convergence | `iam_token_service:sweep_success_rate:ratio_rate_1h` from `iam_token_service_rotation_sweep_total` | 99% — a proxy: the LLD's objective (no `rotating` version outlives `expires_at` by more than one cron interval) has no direct metric | `IAMTokenServiceSLO3_SweepSuccessRateLow` |
| SLO-4 TS-3 read latency | `iam_token_service:ts3_latency_sli:ratio_rate_{5m,1h}`: share of `GET …/service-accounts/:principal_id` requests at or under `le="0.1"` | p99 ≤ 100 ms (LLD) | `IAMTokenServiceSLO4_TS3LatencyFastBurn` (page), `IAMTokenServiceSLO4_TS3LatencySlowBurn` (ticket) |

The registry's `request_duration` buckets have 0.1 and 0.5 boundaries, so both latency targets are measured exactly. Every SLI keeps `domain`, `service` and `environment`.

## HPA

`deploy/monitoring/prometheus-adapter-rule.yaml` exposes `platform_http_requests_per_second` (from `platform_http_requests_total`) as the optional RPS-per-replica input to the server HPA; CPU and memory remain the primary signals. The consumer has no HPA. `platform_queue_depth` (sampled every `SQS_QUEUE_DEPTH_INTERVAL`, default 60s) is its natural scaling signal once ratified; until then it backs only `IAMTokenServiceOffboardingQueueStalled` and, with `platform_dlq_depth`, `IAMTokenServiceOffboardingDLQBacklog`.
